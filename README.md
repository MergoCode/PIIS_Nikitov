# Лабораторна робота №2: Контейнеризація та розгортання ML-моделі з Docker

**Тема:** Контейнеризація та розгортання ML-моделі з Docker (MLOps: від навчання до production-ready сервісу).  
**Мета:** 
1. Розібратися, як влаштована контейнеризація: образ, шар, контейнер, оптимізація розміру.
2. Упакувати інференс-сервіс (аудіокласифікатор голосових команд Speech Commands на PyTorch) у легкий та безпечний Docker-образ за допомогою багатоступеневої збірки (multi-stage build).
3. Налаштувати автоматизований CI-пайплайн (GitHub Actions), виміряти накладні витрати контейнеризації (latency, RAM, час старту).

## 2. Швидкий старт

### 2.1. Встановлення залежностей локально (venv)
```bash
pip install -r requirements-train.txt
```

### 2.2. Навчання та оцінка моделі
```bash
# Навчання моделі з фіксацією seed та збереженням артефактів
python -m src.train --classes yes no up down --epochs 5 --seed 42 --out ./artifacts

# Оцінка моделі на тестовому наборі
python -m src.evaluate --data-dir ./data --model-path ./artifacts/model.pt --labels-path ./artifacts/labels.json
```

### 2.3. Локальний запуск REST API
```bash
uvicorn src.api:app --host 0.0.0.0 --port 8000
```
- Документація Swagger UI: [http://localhost:8000/docs](http://localhost:8000/docs)
- Healthcheck: `GET http://localhost:8000/health`
- Інформація про модель: `GET http://localhost:8000/model-info`
- Інференс аудіофайлу:
  ```bash
  curl -X POST -F "file=@samples/yes.wav" http://localhost:8000/predict
  ```

## 3. Робота з Docker

### 3.1. Збирання оптимізованого Multi-stage образу
```bash
docker build -t kws-api:1.0.0 .
```

### 3.2. Запуск контейнера
```bash
docker run -d --name kws -p 8000:8000 kws-api:1.0.0
```

### 3.3. Перевірка статусу та здоров'я
```bash
docker ps
# Статус контейнера зміниться на: Up ... (healthy)
docker logs kws
```

## 4. Вимірювання та порівняння (Бенчмарк)

Для вимірювання затримок використовується скрипт `scripts/benchmark.py`:
```bash
python scripts/benchmark.py --url http://localhost:8000 --file samples/yes.wav -n 100 --warmup 10
```

*\*Примітка: в Docker збірка проводилася з аргументом швидкого навчання `--build-arg EPOCHS=1`.*

### Аналіз та висновки щодо накладних витрат:
1. **Розмір образу:** Завдяки **multi-stage build** фінальний образ важить лише **308 МБ** проти **~3.6 ГБ** у single-stage варіанті (зменшення у **понад 11 разів**).
2. **Серверна Latency:** Чистий час обробки аудіо та інференсу нейромережі на CPU практично ідентичний: **1.93 мс** локально проти **1.84 мс** у контейнері.
3. **Клієнтська Latency (e2e):** Невелика різниця (~1.8 мс) зумовлена віртуалізованим мережевим стеком Docker (міст bridge / port forwarding).
4. **Холодний старт:** Запуск контейнера потребує додаткових ~1.5 с на ініціалізацію просторів імен (namespaces), cgroups та запуск оточення Linux.

## 5. CI-пайплайн (GitHub Actions)

Файл `.github/workflows/ci.yml` автоматично виконує наступні етапи на кожен `push` та `pull_request`:
1. **Lint** — перевірка якості коду за допомогою швидкого лінтера `ruff check src/`.
2. **Build image** — багатоступенева збірка контейнера з тегом коміту (`github.sha`).
3. **Run container** — фоновий запуск та опитування ендпоінта `/health` до отримання відповіді.
4. **Smoke test API** — валідація ендпоінтів `/health`, `/model-info`, `/predict`.
5. **Quality Gate** — автоматична перевірка якості: якщо точність моделі нижча за 75% (`accuracy < 75.0%`), пайплайн завершується помилкою та не допускає дефектний реліз.

## 6. Відповіді на контрольні запитання

1. **Чим образ відрізняється від контейнера? Що таке шар образу?**
   - *Образ (Image)* — незмінний шаблон, знімок файлової системи та метаданих, що містить інструкції для створення середовища.
   - *Контейнер (Container)* — запущений екземпляр образу, ізольований процес операційної системи зі своїм шаром читання-запису (read-write layer), мережею та просторами імен.
   - *Шар образу (Layer)* — незмінний набір змін файлової системи, створений конкретною інструкцією Dockerfile (`RUN`, `COPY`, `ADD`). Шари кешуються та перевикористовуються.

2. **Навіщо потрібен `.dockerignore` і як він впливає на build context?**
   - `.dockerignore` виключає непотрібні або конфіденційні файли (`.git`, датасети, кеш `.pyc`, середовища `.venv`) з build context.
   - Це значно зменшує час передачі контексту збірки демону Docker та запобігає роздуванню шарів образу.

3. **Як порядок інструкцій у Dockerfile впливає на кешування та швидкість збирання?**
   - Docker перевіряє кеш зверху вниз. Зміна будь-якого шару інвалідує всі наступні кроки.
   - Рідко змінювані інструкції (встановлення системних пакетів та `requirements.txt`) виносяться вгору, а код застосунку (`COPY src/`) — якомога нижче.

4. **Яку проблему розв'язує multi-stage build? Що саме потрапляє у фінальний образ?**
   - Розділяє етап важкої збірки (завантаження датасету, компіляція, навчання моделі) та фінальний runtime.
   - У фінальний образ переносяться лише артефакти моделі (`model.pt`, `labels.json`, `metrics.json`) та код API без важких залежностей тренування.

5. **Чим відрізняються CMD і ENTRYPOINT, EXPOSE і -p?**
   - `ENTRYPOINT` задає фіксовану виконувану команду, а `CMD` — параметри за замовчуванням, які можна перетерти при виклику `docker run`.
   - `EXPOSE` лише документує порти контейнера, тоді як `-p` здійснює реальний прокид мережевого порту хоста в контейнер.

6. **Чому для інференсу варто брати CPU-збірку PyTorch?**
   - CUDA-пакети збільшують розмір контейнера на 3–5 ГБ. Для компактних моделей типу AudioCNN інференс на CPU є надзвичайно швидким (~2 мс), а розмір образу скорочується в рази.

7. **Переваги й недоліки «запеченої» в образ моделі порівняно з моделлю на volume:**
   - *Запечена:* гарантує 100% сумісність версій коду й моделі, автономність контейнера; але збільшує розмір образу та потребує перезбірки при оновленні моделі.
   - *На volume:* дозволяє оновлювати ваги без перезбірки образу; але з'являється зовнішня залежність і ризик несумісності коду з новими вагами.

8. **Навіщо HEALTHCHECK і як його використовують оркестратори (Docker Compose, Kubernetes)?**
   - Дозволяє перевіряти фактичну працездатність програми (HTTP 200 на `/health`), а не просто наявність активного процесу. Оркестратори автоматично перезапускають завислі контейнери і не пускають клієнтський трафік на неготові інстанси.

9. **Чому контейнер не варто запускати від root?**
   - З міркувань безпеки: у разі втечі з контейнера (container breakout) зловмисник отримує root-доступ до хостової системи. Робота під `USER appuser` реалізує принцип найменших привілеїв.

10. **Звідки береться різниця в latency між локальним запуском і контейнером? Чи вона суттєва?**
    - Через накладні витрати віртуалізації мережі (мережевий міст, NAT, проксі Docker Desktop). Різниця складає близько 1-2 мс і не є критичною для більшості веб-сервісів.

11. **Як Docker вписується в CI/CD для ML-моделей?**
    - Забезпечує відтворюваність середовища;
    - Дозволяє реалізувати перевірки Quality Gates (точність, затримка інференсу) перед деплоєм;
    - Спрощує автоматичну доставку готового сервісу на staging/production.
